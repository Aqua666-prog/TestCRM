# Как строился проект

Проект создан с пустого Git-репозитория под конкретные требования тестового задания. Архитектура и исходники другого CRM-проекта не использовались. Работа разбита на содержательные коммиты: настройка приложения, хранение и валидация лидов, ручное создание, Telegram intake, связь с тегами, фильтр, тесты, конфигурация деплоя и документация. История находится в `.git` передаваемого проекта.

Сначала определён общий контракт Lead и построена модель данных. Затем реализована веб-форма, создающая Lead через общий сервис. После этого добавлен Telegram webhook с последовательным сбором тех же полей. Последними продуктовыми шагами стали теги и фильтрация. Проверки добавлены до подготовки отчёта: они проверяют не только отдельные функции, но и связанный путь webhook → база → HTML → назначение тегов → фильтр.

## AI и самостоятельность решений

Использовался Codex в ChatGPT Work Mode: генерация и редактирование Python/HTML/CSS, запуск команд, тестов и анализ результатов. Субагенты, Replit Agent, Base44 и готовая архитектура стороннего приложения не использовались. Навык Sites был изучен для оценки хостинга; его Workers-runtime не выбран, поскольку он не соответствует предпочтительному Python/PostgreSQL-стеку.

Это AI-assisted реализация: нельзя честно заявлять, что кандидат вручную написал весь код. Требования, приоритеты, единая модель Lead, стек и исключение MTProto из обязательного объёма заданы кандидатом. Конкретные решения в этом проекте: один небольшой FastAPI-процесс, server-rendered Jinja2, отдельный сервис создания Lead, many-to-many теги, состояние диалога и журнал обработанных обновлений в БД, короткая блокировка intake-транзакций, повтор доставки сохранённого ответа после сетевого сбоя. Они непосредственно решают требования MVP. Кандидату необходимо понимать эти решения и воспроизвести развёртывание перед защитой работы.

## Проверка и ограничения

Локальные тесты проходят; отдельно проверен реально запущенный HTTP-сервер с тестовым отправителем Telegram. Приложение развёрнуто на Railway: Dockerfile, PostgreSQL с volume, HTTPS, production healthcheck. Через Railway CLI настроен и проверен настоящий Telegram webhook. Ручная HTML-форма, два тега, фильтры и снятие тегов проверены на production. Реальный диалог пользователя с ботом завершён: Telegram-лид №2 появился в CRM, получил два тега и найден обоими фильтрами. Проверка зафиксирована в TEST_REPORT. Подмена отправителя находится только в tests и отсутствует в production Docker image.

Для инфраструктуры использовались Railway plugin, cloud browser для начальной настройки и официальный Railway CLI для загрузки локального проекта. Railway Agent не использовался. Обнаруженное устаревание Config-as-Code учтено: настройки запуска и health заданы непосредственно сервису. При проверке исправлено ожидание регистра тегов в acceptance-скрипте и добавлена поддержка SOCKS только в рабочее окружение проверок, без изменения production-зависимостей.

## Дополнительная неделя

После рабочего деплоя: миграции Alembic для изменения схемы, ограничение частоты входа и заявок, журнал действий менеджера, пагинация при росте списка, резервные копии с проверкой восстановления и автоматизация CI. Если подтвердится потребность в личном Telegram-аккаунте — отдельный MTProto-worker с безопасным хранением сессии и дедупликацией внешних сообщений. Расширения следует добавлять после реального использования основного сценария.
